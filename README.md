# Emumee

Emumee is an experimental Windows malware analysis tool. It emulates x86/x64
user-mode PE files and selected .NET assemblies in an isolated worker, then
produces JSON reports, extracted artifacts, and a local read-only dashboard.
See [coverage and safety](COVERAGE_AND_SAFETY.md) for measured behavior and
known limits.

| Input | Current handling |
| --- | --- |
| EXE, SCR, and other user-mode PEs | Emulated by file content |
| DLL, OCX, CPL, AX | DLL attach; optional `--all-exports` with placeholder arguments |
| MSI, MSP, MST | Static stream inspection and payload recovery; no installer action execution |
| SYS and scripts | Not supported as primary inputs |

**Security:** Treat unknown files as hostile. Read [SECURITY.md](SECURITY.md)
before using the tool on real samples. The project is licensed under [MIT](LICENSE).

Emumee is a Windows-only, user-mode PE analysis tool. It runs x86 and x64 native PE code in [Speakeasy](https://github.com/mandiant/speakeasy), which uses Unicorn CPU emulation and modeled Windows APIs. Managed PEs use Emumee's bounded CIL interpreter. A command-line runner produces JSON reports and extracted artifacts; a read-only website displays the runs.

Compatibility is currently strongest for the documented harmless loader, DLL, file, registry, process, network, and extraction fixtures. It is not yet a general Windows 11 application runtime. The packaged worker now exercises guest-owned narrow and wide CRT argument arrays, correctly terminated guest environment blocks, and stable guest UCRT standard stream pointers on x86 and x64. Real Windows `whoami.exe` with its explicitly staged `en-US/whoami.exe.mui` resource file completes on x86 and x64; `/all` prints the persona user, SID, groups, privileges, and local claims status. Real Windows `hostname.exe` also completes on x86 and x64 and prints the persona hostname. The same `whoami.exe` without its MUI file may follow an error path. There is no representative malware corpus or measured percentage for average-program coverage. See [COVERAGE_AND_SAFETY.md](COVERAGE_AND_SAFETY.md) for the exact release evidence and remaining anti-analysis gaps.

In the 2026-10-12 build, the packaged worker runs two supplied x64 EXEs past their formerly unsupported AVX startup instruction. Both runs finish with no recorded errors and 11 extracted artifacts. The fallback covers only the documented AVX shapes; use `.\tools\run_avx_cases.ps1` to repeat the harmless x86/x64 checks.

See [COVERAGE_AND_SAFETY.md](COVERAGE_AND_SAFETY.md) for researched gaps,
current observations, and verification steps.

## Start

Requires Windows 11 and Python 3.11 or newer. `setup.ps1` installs dependencies and builds the isolated worker executable. A .NET SDK is only needed to build the harmless managed test fixture. Run `build.ps1` after changing worker code.

```powershell
.\setup.ps1
.\emumee.ps1 persona
.\emumee.ps1 run .\sample.exe --dll .\companion.dll
.\emumee.ps1 run .\installer.msi
.\emumee.ps1 run .\sample.scr
.\emumee.ps1 run .\control.cpl --all-exports
.\emumee.ps1 run .\sample-folder --launch app\main.exe
.\emumee.ps1 run .\sample.exe --file .\config.bin --files-dir .\support-files
.\emumee.ps1 run .\sample.exe --guest-arg=--stage-one --guest-env MODE=analysis
.\emumee.ps1 run .\downloader.exe --network-fixtures .\examples\http-fixtures.json
.\emumee.ps1 run .\downloader.exe --network-fixtures .\examples\http-fixtures.json --offline-replay
.\emumee.ps1 batch .\samples --output .\output
.\emumee.ps1 dashboard
```

Open <http://127.0.0.1:8765> for the local dashboard. Each run is stored under `output/<run-id>/` and includes `summary.json`, `engine-report.json`, an artifact manifest, extracted bytes, and worker logs.

`run DIRECTORY --launch RELATIVE_PATH` recursively stages the directory's files, preserves their paths in the guest filesystem, and launches the chosen PE. The guest working directory is the launch file's directory. Matching native or managed DLLs are discovered as companions automatically; other files remain available to guest file APIs. With a direct PE input, repeat `--file PATH` for individual files placed beside it or `--files-dir DIRECTORY` for recursively staged files. A package is limited to 2,048 files, 32 MiB per file, and 64 MiB total. Links, junctions, hardlinks, path collisions, and ambiguous matching DLL basenames are rejected before launch. The run manifest lists every staged file and hash, and both parent and worker verify staged bytes. Run `.venv\Scripts\python.exe tools\verify_file_bundle_package.py` for harmless packaged x86/x64, managed, supplemental-file, and link-denial checks.

Windows programs with external MUI resources can include a matching locale subtree in the staged directory, for example `program.exe` alongside `en-US/program.exe.mui`. `LoadStringW` reads only those explicitly staged guest bytes. The version resource APIs read the submitted PE or staged guest PEs; token user, groups, privileges, and SID lookup use the configured persona. Bounded privilege-name lookup and a local-only Kerberos domain-policy response support the `/all` path. Other LSA packages, domain policy requests, and nonempty ticket caches remain unsupported. Microsoft binaries are not included in this repository.

Direct `.msi`, `.msp`, and `.mst` inputs receive bounded, read-only compound-file stream inspection inside the isolated worker. Embedded PE streams and CAB streams are saved as artifacts; PE bytes embedded within other streams are carved. This is static payload recovery: installer tables, CAB contents, and custom actions are not interpreted or executed, so these runs are reported as `partial`. Extracted PE artifacts can be submitted separately with `run`, and an already unpacked installer directory can use `run DIRECTORY --launch RELATIVE_PATH`. No host `msiexec` process is started.

Native DLL-style PEs, including `.dll`, `.ocx`, `.cpl`, and `.ax`, run their attach entry point by default. `--all-exports` additionally asks Speakeasy to emulate its first ten exports with placeholder arguments. This can expose behavior behind an export but does not reproduce a real Control Panel, COM registration, or `rundll32` call signature; an export that needs specific arguments may stop with a partial report.

`batch` analyzes up to 1,000 EXE, SCR, COM (when PE), MSI, MSP, and MST files in a directory, sequentially through the same isolated `run` path. Add `--recursive` to include subdirectories, `--include-dll` to include DLL, OCX, CPL, and AX inputs, or `--all-pe` to include PE files with other extensions. Direct `run` accepts a PE under any filename; its bytes determine whether native or managed emulation applies. It does not follow filesystem links. The command prints one JSON line per sample and a final `batch_summary` line; it returns a nonzero status if any sample was partial, failed, or rejected. Use `--max-samples` to set a lower cap. Other analysis options such as persona, limits, arguments, and explicit companion DLLs apply to every sample in the batch.

The CLI and dashboard show the modeled guest exit code, instruction count, instruction-limit and wall-clock timeout outcomes, and denied network-operation count separately from analysis status. Each summary contains a run manifest with the worker EXE and complete bundle-tree SHA-256, input and companion hashes, persona hash, guest arguments/environment, and effective time, instruction, memory, and output limits. The dashboard can filter by sample hash and compare two runs' outcomes, persona fields, invocation inputs, API counts and return values, behavior counts and order, console output, and unique artifact hashes. Identical artifact bytes are grouped by SHA-256 while each extraction observation remains as provenance.

Run detail pages paginate engine and network broker events at 2,000 per page. The `artifact_capture` field records bounded size and memory-scan omissions, with counts, bytes, reasons, and examples; the dashboard highlights any omissions.

For new completed and partial runs, the parent records SHA-256 and byte size for `engine-report.json` and `network-broker.json`. The dashboard verifies those files before showing the detail or comparison view; older runs are labeled as unbound. This detects changes after the parent recorded the reports, but it does not authenticate data written by a compromised worker or broker. Artifact-group verification reads only bounded PE header fields in the unrestricted parent; richer PE parsing remains inside the isolated worker.

While a run is active, the raw network broker journal is a broker-only file beside the run directory. The worker has no access to that file; the parent recovers bounded events from its open handle, writes `network-broker.json`, and removes the private journal. This prevents a compromised worker from directly rewriting the broker's journal, but it does not make the broker itself or its modeled network behavior infallible.
The private journal counts toward `--max-output-mb`, and both isolated jobs stop if the combined run output crosses that limit. The CLI rejects `--output` paths inside the worker bundle to keep the private journal outside the worker's bundle read grant.

`--network-fixtures` accepts a version-1 JSON file such as [examples/http-fixtures.json](examples/http-fixtures.json). Every rule specifies an exact request method, full URL, `chunked` flag, complete guest-supplied header set, and complete body. Matching occurs at the broker boundary, before the HTTP transport could add headers such as `Host` or `Content-Length`. Header names match without regard to case; header values, URL, and body bytes match exactly. Bodies use either `body_utf8` or canonical `body_base64`, including an explicit empty body. The response supplies status, reason, HTTP version, ordered headers, and exact body bytes. A match is served inside the network broker before DNS resolution or a host connection; unmatched requests use the normal broker policy. The normalized full definitions are saved as `network-fixtures.json` in the run and downloadable from its dashboard page. Broker events record the rule ID, request/response headers, body lengths, and SHA-256 hashes. This applies to modeled HTTP(S) fetches, not raw sockets.

A standard .NET apphost EXE bound to an adjacent same-name managed DLL is recognized by its binding marker. Only that exact DLL is read and sent to the CIL interpreter; both the submitted apphost and execution-target hashes appear in the run manifest. Other native inputs continue through CPU emulation.

Guest console text is now stored in `console_output.stdout` and `console_output.stderr` in both `summary.json` and `engine-report.json`, and shown in separate sections on each dashboard run page. Native capture covers successful `WriteFile` calls to the modeled standard handles and `WriteConsoleA/W`; managed capture covers `Console.Write/WriteLine` and `Console.Out/Error` writer calls. Each displayed stream is limited to 128 Ki characters and has a `*_truncated` flag. Native byte output is decoded as UTF-8 with replacement for invalid bytes, so legacy console code pages and binary output may not display exactly. Older reports have no console capture field; rerun a sample to populate it. These are guest bytes and are never printed by the worker to host stdout.

The CLI starts two bundled processes in separate, fresh Windows AppContainers. The emulation worker has **no network capability**. The network broker has `internetClient` and accepts only bounded network requests through fixed streams in `broker-ipc`. The worker writes to the current run directory. The broker can traverse that directory but has write access only to `broker-ipc` and its separate private journal; it can read an exact fixture file when one is supplied. Separate Windows jobs limit memory and each container to one host process; a watchdog limits run-directory size and file count. The private worker and broker modes also enable and verify Windows' child-process restriction before handling sample or network data. Profiles are deleted and access grants revoked after each run. Runs sharing one bundle are serialized so their temporary access grants cannot race. If the bundle is absent or incompatible, the CLI refuses to start analysis. Guest PE code runs only through CPU/API emulation.

Nonempty HTTP request bodies from modeled native and managed calls are saved as `network_request_body` artifacts before the broker is contacted, including when the broker denies a destination. Each body is capped by the 16 MiB transfer limit, and these artifacts have a 64 MiB cumulative extraction quota per run. The manifest records the guest URL, size, and SHA-256; a quota skip is visible in network events. The artifact means the guest attempted to send those bytes, not that the destination received them.

`--persona persona.json` accepts a JSON file with the fields printed by `emumee persona`. The default profile describes a Windows 11 Pro desktop with common user folders, 29 small document and configuration files, 48 Windows and user registry keys, and 18 modeled process snapshots. The files and registry include matching recent-document and Explorer activity. It can be changed for hostname, user, privilege level, Windows build, virtual files, registry entries, process names, UTC offset, clock, uptime, physical/available memory, and the modeled Intel CPU brand, signature, core/thread count, and frequencies. CPU fields can be supplied as a partial `"cpu"` object. Changing the user, hostname, CPU, or build refreshes dependent default files and registry values. For example:

```json
{
  "hostname": "DESKTOP-A1B2C3",
  "user_name": "Morgan",
  "windows_build": 22631,
  "clock_utc": "2026-10-09T14:00:00Z",
  "virtual_files": [{"path": "C:\\Users\\Morgan\\Documents\\note.txt", "text": "hello"}]
}
```

Omitted fields keep their default values. The process list is a modeled snapshot; its named Windows programs are not automatically loaded or executed. The default guest has two generated runnable PEs: `C:\Windows\System32\hostname.exe` prints the persona hostname, and `C:\Windows\System32\whoami.exe` prints the local computer and guest user. Both execute guest WinAPI calls under CPU emulation. To run other child programs, explicitly stage their PE bytes with a package directory, `--file`, or `--files-dir`. Guest `CreateProcessA/W` and `WinExec` can resolve guest programs by full path, current directory, `C:\Windows\System32`, or `C:\Windows`, with an optional `.exe` suffix. Guest child code runs through CPU emulation; no host Windows process is launched. The native engine takes sample bytes directly, so it does not mount the input's host directory. Only supplied files, supplied or automatically discovered DLLs, the generated utilities, and configured virtual files are initially visible through guest filesystem calls. An EXE can also write a native DLL into its virtual filesystem and load it from those guest bytes without creating a host DLL file. Companion and guest-created DLLs are loaded as guest PE modules. Statically imported companion exports are linked to guest code and initialized before the EXE entry point. A bounded chain of supplied static DLL imports initializes its leaf before its parent, including a tested TLS callback. When a supplied DLL's preferred base is occupied, the loader checks its relocation blocks and maps it at another guest base only for supported x86/x64 fixups; tested collision probes call the relocated export, while missing and malformed relocation controls fail. A tested guest-created DLL can call an imported WinAPI or an export from an explicitly supplied companion DLL; the companion's process-attach entry runs before the guest DLL's entry. For tested x86/x64 DLLs, TLS callbacks run before the process-attach entry point on supported dynamic `LoadLibrary` paths. Exported functions returned by `GetProcAddress` execute under CPU emulation.

`GetComputerNameA/W`, `GetComputerNameExA/W`, and `GetUserNameA/W` now use persona values and enforce the Win32 buffer-size contracts. The DNS forms use the persona's `domain` field as the DNS suffix unless it is `WORKGROUP`.
`GetEnvironmentVariableA/W` returns the copied character count on success, the required count for a small buffer, and an explicit error for an absent variable.

The default native drive view contains one C: volume. `GetVolumeInformationA/W` reports a consistent NTFS label, serial, component length, and capability flags, and rejects missing drives or undersized buffers. `GetTempPathA/W` follows the guest `TMP`, `TEMP`, and `USERPROFILE` values and reports the required buffer length before writing. These are modeled API responses; NTFS features such as named streams and hard links are not fully implemented in the guest filesystem.

The bounded dependency loader also supports a guest-created DLL importing another guest-created DLL in the same virtual directory, including a nested explicitly supplied companion. The DLLs attach in dependency order and detach in reverse order when their references reach zero. Guest-created DLL mappings share a 32-module aggregate limit and a 64 MiB byte budget across direct, dependency, and forwarder loads. `tools\verify_guest_module_budget.py <output-root>` checks packaged x86/x64 fixtures that map 32 distinct guest DLL paths and refuse the 33rd load. When a guest-created DLL or its guest-created dependency must move from its preferred base, the loader validates supported relocation blocks before mapping; x86/x64 collision fixtures run valid fixups and reject absent or malformed blocks. Named and ordinal PE export forwarders can resolve through already loaded guest modules with a depth and cycle limit; tested missing targets fail visibly. Dynamic `GetProcAddress` can also map an explicitly supplied or guest-created forwarder target that was not yet loaded, run its entry under emulation, and release it with the forwarding DLL. Guest-created targets are resolved from the forwarding DLL's sibling path in the virtual filesystem, never from a host DLL path. Two-hop, relocation, initialization-failure, and unload cases are covered by harmless fixtures. `tools\verify_forwarded_exports.py <output-root>`, `tools\verify_implicit_forwarders.py <output-root>`, and `tools\verify_guest_forwarders.py <output-root>` check their packaged reports. A tested import cycle fails visibly and a retry remaps from guest bytes. A static EXE import can also resolve an unloaded explicitly supplied forwarder target, initialize each target before its forwarding DLL, and reject missing relocation or a failed attach; `tools\verify_static_implicit_forwarders.py <output-root>` checks those packaged cases. A dynamically loaded DLL can also bind an IAT import through an unloaded forwarder target in either explicitly supplied DLL bytes or its virtual sibling directory. The dependency walk attaches leaf before middle and releases those modules in dependency order; `tools\verify_dependency_forwarders.py <output-root>` checks the packaged cases.
Direct `ntdll.LdrLoadDll`, `LdrGetProcedureAddress`, and `LdrUnloadDll` now use the same guest DLL mapping, export, reference-count, and detach path for bounded counted strings and zero load flags. Harmless x86/x64 fixtures load a supplied DLL, call its export, and unload it; TLS attach and detach are also tested. Custom NT loader search paths and nonzero flags return an explicit unsupported status.
Tested x86/x64 guest DLLs with the same basename can coexist when loaded by distinct full guest paths. A later basename-only `LoadLibraryW` retains the first loaded module; `tools\verify_guest_same_basename.py <output-root>` checks the packaged handle choice, extracted bytes, and broker closure. DLL redirection, API sets, KnownDLLs, broader directory search, delay imports, and loader reentrancy remain incomplete.

For a statically imported companion, a failed `DllMain(DLL_PROCESS_ATTACH)` stops before the EXE entry point and makes the analysis partial. The failing DLL then receives guest TLS/process-detach callbacks, followed by previously attached dependencies in reverse order. TLS callbacks receive a zero reserved argument; tested `DllMain` calls distinguish failed load from process termination. A supplied DLL with TLS callbacks and no entry point can initialize an export and receive TLS detach if a later DLL fails. Successful static attach and TLS callbacks continue into the EXE. Windows loader-failure exit codes and untested initialization paths remain incomplete.

## Network and extraction

Modeled outbound WinSock and WinINet/WinHTTP calls go through the separate broker AppContainer and use the host's existing route, including Mullvad when it is active. Broker requests and outcomes are recorded in `network-broker.json`; guest API attempts and outcomes appear in `engine-report.json`. Invalid InternetOpenUrl, HttpSendRequest, WinHttpSendRequest, and gethostbyname calls are logged before they can reach the broker. If the broker is unavailable, these modeled calls fail closed and log the denial. The broker limits each run to 4,096 requests and 128 open sockets and bounds URLs, headers, and transfers. Host-local, private, multicast, and reserved IP destinations are denied; guest inbound sockets are denied. Emumee does not check whether Mullvad is connected. Tested native WinINet GET/POST and WinHTTP POST calls forward bounded custom headers and exact body bytes through the broker. WinINet POST fixtures exercise InternetConnect, HttpOpenRequest, and HttpSendRequest; invalid staging handles and oversized guest strings fail before the API model or broker. Fixed-length WinHTTP POSTs can send optional bytes followed by bounded `WinHttpWriteData` chunks; the broker request occurs when `WinHttpReceiveResponse` is called with the complete body. Tested WinHTTP chunked POSTs require the transfer header, ignore-total-length value, null optional data, and a final zero-length write; the broker produces HTTP chunk framing from bounded guest body bytes. Fixed-length WinINet POSTs can stage an `INTERNET_BUFFERS` body, append bounded `InternetWriteFile` bytes, and send the complete body through the broker at `HttpEndRequest`. A linked `INTERNET_BUFFERS.Next` node is recorded but ignored, matching a harmless probe on this Windows 11 host. Tested `InternetReadFile` and `WinHttpReadData` calls return sequential brokered response bytes and counts. Tested synchronous `InternetQueryDataAvailable` and `WinHttpQueryDataAvailable` calls report bytes remaining in the buffered broker response after reads. Tested `HttpQueryInfo` and `WinHttpQueryHeaders` levels return the brokered status code, common or custom headers, and raw CRLF headers with bounded buffer handling. Closing a tested HTTP request or its parent session invalidates its cached response. Asynchronous modes, other query flags, and less common Windows networking APIs remain incomplete; some retain Speakeasy's simulated behavior and do not reach the live network.

Exact HTTP fixtures still fall through to live networking by default when a request does not match. Add `--offline-replay` to use only exact fixtures: unmatched HTTP requests, DNS requests, and raw socket operations are denied and logged as replay misses. In this mode the broker has no internet capability. The run manifest records the mode, and the network-attempt summary labels fixture responses and replay misses. An offline run without fixtures denies all modeled outbound requests.

The broker records validated DNS, socket connection, send, receive, and HTTP attempts before address resolution or network I/O, including policy-denied destinations. HTTP socket connections use the validated literal IP while retaining the original hostname for HTTP and TLS; a harmless changing-DNS test confirms one lookup and a socket target matching the logged address. Successful operations also record resolved addresses, actual byte counts, response status, and hashes where available. Each bounded event is also written to a journal before network I/O. The parent holds that file open from before either sandboxed process starts and recovers a bounded prefix if the broker exits abruptly; it marks the run and dashboard log incomplete. The dashboard shows recent broker events, and `network-broker.json` retains the recovered report. These logs describe modeled broker operations; they cannot prove visibility after a broker compromise or host power loss.

Emumee collects guest file writes, completed dropped files, PE images found in memory, executed dynamic-code regions, script-like decoded strings, and network transfer bytes. The managed interpreter also captures GZip, Deflate, and zlib output from tested bounded `Read` and `CopyTo` decompression over guest `MemoryStream` or `FileStream`, up to 32 MiB per decoded artifact. Compressed reads consume bounded guest chunks and preserve source position; invalid compressed data raises a catchable managed error. Compression mode, exact .NET read-ahead, async/span overloads, and additional formats remain incomplete. Its virtual file map supports tested `File.Exists`, `ReadAllText`, `ReadAllBytes`, `WriteAllText`, `WriteAllBytes`, `AppendAllText`, and `Delete` calls; relative names resolve against the persona current directory, and deleted guest files remain available as earlier extracted artifacts. Tested managed `File.OpenRead`, `OpenWrite`, `Create`, `Open`, and `FileStream` constructors use guest-only stream handles with synchronous byte reads/writes, position, length, seek, resize, sharing checks, and close. Async and span operations, locking, deletion through an open stream shared for deletion, and broader overloads remain incomplete. Managed strings and individual virtual files are capped at 32 MiB; console output, trace events, and the in-memory guest file store have separate limits. Hitting one makes the run partial. Artifacts are content-addressed by SHA-256. The parent checks their manifest, size, and hashes before accepting a completed run. For a download, the dashboard hashes the bytes it has read and serves those same bytes, so a later file replacement cannot change the response. Extraction is best effort: a memory blob without a PE header or executed dynamic-code event may require manual review of the engine report.

Tested managed `ZipFile.ExtractToDirectory` overloads read an archive from a guest path, `MemoryStream`, or `FileStream`, and write stored or Deflate entries into guest directories. `ZipFile.OpenRead` and read-mode `ZipArchive` support exact `GetEntry` lookup, `Entries` indexing and `foreach`, and `ZipArchiveEntry.Open` as a bounded guest stream. Opened PE entries are classified as PE artifacts even when never written to a guest path. A compiled harmless loader also selects a DLL from `Entries`, copies its bytes into guest memory, loads it with `Assembly.Load`, and invokes a public method entirely through CIL interpretation. A bounded scan of ZIP central-directory headers limits entry count to 1,024 and directory metadata to 4 MiB before the ZIP parser allocates entry objects. The model checks extraction paths stay inside the selected guest destination, rejects links and unsupported compression, and caps decoded data at 32 MiB. Existing-file collisions remain catchable unless overwrite is requested. ZIP64 central directories, multi-volume archives, ZIP creation, password-protected archives, entry metadata fidelity, and broader archive APIs remain unsupported or incomplete.

For a managed EXE, `--dll` supplies a managed companion DLL by assembly manifest name to the guest interpreter. Tested `Assembly.Load("Name")` resolves only those explicitly supplied bytes and can invoke a public method through guest CIL reflection. Tested compiled references call public static and instance methods in a supplied companion when the assembly name, type, method, and CIL signature match. For a same-module base/derived chain inside either an EXE or supplied DLL, tested `callvirt` dispatches a matching override, preserves a `new virtual` shadow slot, and leaves a nonvirtual base call on its declared method. A missing companion raises a guest `FileNotFoundException`; the host CLR and DLL search paths are never used. Qualified assembly identities, version/public-key binding, cross-DLL inheritance, interface/explicit overrides, generic calls, custom resolution handlers, and mixed AnyCPU architecture rules remain incomplete.

Managed instance-field reads return tested .NET defaults for primitive numeric fields, strings, objects, and single-dimensional arrays, including inherited fields. Unsupported value-type layouts and unusual field signatures remain visible as partial runs.

Supported `URLDownloadToFileA/W` and `URLDownloadToCacheFileA/W` calls also use the broker. Returned bytes are written only to the guest filesystem and captured as artifacts; the cache variant writes its virtual cache path into guest memory. Unsupported callback or bind-host modes are marked partial. A configured host-backed virtual path cannot be replaced by a download. Harmless fixtures exercise success through a local test broker and packaged denial of a host-local destination.

Managed file writes require an existing guest parent directory. The CIL model seeds Windows, persona, and current-directory paths, and supports tested `Directory.Exists`, `Directory.CreateDirectory`, empty `Directory.Delete`, and bounded `Directory.Delete(path, true)` operations without touching host directories. Recursive deletion removes guest descendants, retains previously extracted payloads, and refuses a tree containing the guest current directory. Tested `Directory.GetFiles`, `GetDirectories`, and `GetFileSystemEntries` calls return bounded top-level or recursive arrays from the guest namespace, including guest filename casing; simple `*` and `?` patterns are modeled. Tested `File.GetAttributes` and `File.SetAttributes` calls keep ReadOnly, Hidden, System, Archive, Normal, and Directory flags in guest state; read-only files reject guest writes, deletes, and overwrite copies, and a recursive directory delete rejects a read-only descendant. `Path.GetTempPath`, `Path.Combine`, and `Directory.GetCurrentDirectory`/`SetCurrentDirectory` use persona and mutable guest state; relative guest paths follow that state while the host working directory stays unchanged. Pattern path components, 8.3 filename matching, broader attribute flags, open-handle and linked-entry behavior, and exact .NET error fidelity remain incomplete.

Tested managed `File.Copy` and `File.Move` paths use the same guest-only namespace. Copying or moving a persona file reads only the worker's virtual bytes, and successful destinations are captured as artifacts. `File.ReadAllBytes` returns an independent mutable guest byte array, so editing the returned array does not edit the virtual file until a guest write call. Existing-target collisions and overwrite requests are checked before the guest map changes. Sharing, read-only attributes, and some Windows path corner cases remain incomplete.

Tested managed `MemoryStream` constructors, synchronous reads/writes, seek, resize, `ToArray`, and `Stream.CopyTo` move bounded bytes between guest memory and guest `FileStream` objects. A byte-array-backed stream retains its guest array and cannot grow past that array's capacity. A compiled fixture checks both copy directions, positions, and recovered payloads. Async operations, span overloads, broader constructors, and exact buffering behavior remain incomplete.

Managed AES supports tested `Aes.Create`, `AesManaged` and `AesCryptoServiceProvider` construction, explicit 128/192/256-bit keys and IVs, CBC/ECB, None/PKCS7 padding, `TransformBlock`, and `TransformFinalBlock` over guest byte arrays. Padded decryption holds its last block until finalization; successful output from all blocks is scanned together for a PE, even if guest code never writes a file. Successful decryption also saves the combined plaintext as a memory artifact, including non-PE configs and scripts. Capture is bounded to 128 observations and 64 MiB per run; transform events and the summary record hashes and omitted bytes when that budget is reached. A harmless managed program recovered a memory-only JSON blob in the packaged AppContainer. Harmless compiled fixtures check the published NIST AES-128-CBC vector, padding, output windows, transform reuse, and catchable input errors. Tested `CryptoStream` read/CopyTo and write/final-flush paths wrap guest `MemoryStream` or `FileStream` objects; read mode consumes bounded ciphertext chunks, can return partial plaintext, and finalizes at guest EOF. Bounded `Rfc2898DeriveBytes` constructors, `GetBytes`, `Reset`, and the one-shot `Pbkdf2` byte-array overload derive guest AES keys with SHA-1/SHA-256/SHA-384/SHA-512; a compiled fixture checks SHA-1 stream continuation and SHA-256 AES payload recovery. PBKDF2 passwords are redacted in its call trace, and derivation events contain only algorithm, iteration count, and output length. AES transform events record sizes and hashes rather than key bytes; guest string arguments elsewhere in the managed call trace may contain encoded keys. Exact .NET buffering, async/span streaming, nested CryptoStreams, other cipher modes and padding, automatic key/IV generation, other PBKDF2 overloads, and the wider .NET cryptography API remain incomplete.

Tested managed `WebClient.DownloadData`, `DownloadString`, and `DownloadFile` calls use the logged network broker. `DownloadData` returns a mutable guest byte array; `DownloadFile` saves received bytes into the virtual guest filesystem and extracts them as an artifact. A denied private destination raises a catchable managed `WebException`. Supported address forms are a string or a simple `Uri` object; BaseAddress, QueryString, custom encodings, callbacks, async methods, and other schemes remain incomplete.

Tested managed `HttpClient.GetByteArrayAsync`, `GetStringAsync`, `GetAsync`, `PostAsync`, and `SendAsync(HttpRequestMessage)` calls use the broker. `PostAsync` and `SendAsync` accept bounded guest `StringContent` or `ByteArrayContent` bodies. `StringContent` sends UTF-8 and a content type; `ByteArrayContent` honors an offset/count window and pre-send byte-array changes. `SendAsync` supports a bounded method/URI request, client default headers, and request headers; malformed or restricted headers and reuse of a sent request fail visibly. Tested `BaseAddress` use combines path-relative, root-relative, and parent-relative request paths before broker validation and locks the property after a request starts. ## Current limits

This is a working analysis foundation, not a gap-free Windows 11 implementation. Speakeasy stops when an unimplemented API is needed; Emumee's managed interpreter supports a subset of CIL and framework calls, including selected catch, finally, rethrow, module-backed byte array, switch, and in-memory assembly reflection paths and modeled exceptions from Base64 decoding and virtual file reads. Tested byte-array index, reference, and null-length failures route catchable managed exceptions; broader array type and reference fidelity remain incomplete. Byte-loaded managed DLL/EXE stages can execute public static or basic instance methods, or an entry point under CIL interpretation, with a limit of 16 loaded assemblies, 64 MiB of loaded assembly bytes, and 20,000 guest objects per run. Managed filter/fault clauses, general exception inheritance, reflection overloads, inheritance and field defaults, dependency resolution, and full directory/attribute semantics for virtual files remain unsupported or incomplete. TLS and process attach run for tested companion and guest-created DLL paths, including bounded recursive static and dynamic dependency chains; broader Windows search-order behavior, same-basename modules already loaded from different paths, `LoadLibraryEx` flag modes for guest-created DLLs, and untested initialization-failure paths remain incomplete. Guest-created DLLs have tested load reference counts and execute TLS and process detach in guest CPU when the count reaches zero; the module is then removed from guest loader state and memory. `FreeLibrary` tracks tested dynamic and static references to explicitly supplied companions, runs TLS and process detach at zero, and unmaps the module. A guest DLL also releases its companion dependencies on unload. Unloading system DLLs remains unsupported and marks the run partial. For tested dynamic `DllMain` failures, Emumee runs process detach, unmaps the failed DLL and newly mapped dependencies, and permits a fresh load attempt. A failed static attach stops before the EXE entry and reports partial; complete process-termination and detach behavior remains incomplete. `MoveFileExA/W`, `DeleteFileA/W`, and `CopyFileA/W` change tested guest-created and exact persona files in the virtual filesystem without changing backing host files; the copy hook uses in-memory persona bytes for configured sources. Basic `CreateDirectoryA/W`, `RemoveDirectoryA/W`, and `GetFileAttributesA/W` state is modeled for tested paths. Pattern-backed mappings, file attribute and symlink fidelity during copying, open persona-backed destination sharing, non-guest delete-on-close modes, cross-process handles, overlapped I/O, large sparse offsets and unbuffered seek alignment, extended file attributes, and some move flags remain partial. Guest-created entries appear in Speakeasy's `FindFirstFile` walker. Basic `GetFileAttributesExA/W` returns guest-only attributes, virtual timestamps, and size for tested files and directories; per-file historical timestamps and broader attributes remain incomplete. It does not execute the host CLR, PowerShell, `cmd.exe`, or kernel drivers. Child native PEs use Speakeasy's child emulation. Registry value writes, queries, and basic key creation/open/close/delete are modeled for tested paths; access rights, registry views, notifications, and broader value types remain incomplete. Unsupported paths appear in the run report.

Windows [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) provides the OS access boundaries; [job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) supply resource limits. The network-disabled worker cannot create a direct internet socket in the sandbox probe. A compromised broker has its own network capability, so complete logging cannot be guaranteed after a broker compromise. Neither sandbox is a guarantee against emulator or Windows vulnerabilities. A VPN changes routing and does not provide host isolation. Keep high-risk samples on a dedicated analysis machine while these limits remain.

Temporary AppContainer ACL changes use `icacls /L` and reject redirected grant roots. `tools\reparse_acl_smoke.py` checks harmless child and root junctions against a sibling directory ACL; it does not establish safety for every reparse type or race. A packaged LPAC probe failed before the worker reached its first stage marker on this host, so the regular AppContainer remains the active boundary.

The output watchdog counts ordinary file bytes and named Windows data streams on run files, directories, and the private broker journal; an uninspectable path stops the worker and broker jobs. The residual ACL scan checks files and directories. These are periodic checks, so short-lived streams and other filesystem races remain possible.

The bundled executable has PyInstaller's Control Flow Guard flag removed because [Unicorn crashes with that bootloader flag](https://github.com/pyinstaller/pyinstaller/issues/9352). This reduces one exploit mitigation on the worker process; AppContainer and the job remain in force.

The engine is based on [Speakeasy 2](https://github.com/mandiant/speakeasy), whose [limitations](https://github.com/mandiant/speakeasy/blob/master/doc/limitations.md) also apply here. The managed parser uses [dnfile](https://github.com/malwarefrank/dnfile) and [dncil](https://github.com/mandiant/dncil).

The parent bounds input size and validates the PE header before launch. Inside AppContainer, the worker rejects native entry points and import-directory ranges that lie outside the declared image and records a specific failed summary. `tools\malformed_pe_package_smoke.py` exercises fifteen deterministic mutations of harmless x86, x64, and managed fixtures. Native emulation faults keep their structured detail in `engine-report.json` and produce bounded string errors in the summary; the four tested x86/x64 truncated-section and changed-byte cases now report partial results rather than losing their worker summaries at parent validation. If a worker stops before finishing, the parent collects the broker journal and recovers only hash-verified artifacts from the last bounded worker checkpoint. The report marks the guest trace incomplete; later observations may be missing. Run `.venv\Scripts\python.exe tools\verify_artifact_checkpoint_package.py` to exercise this path with a harmless managed guest that writes a payload and loops until timeout.

Parent and dashboard report readers use the opened Windows file handle to check the final path, reparse attribute, hard-link count, and size before reading worker-owned content. Extracted artifact bytes are also checked against their recorded SHA-256. A failed artifact-manifest check quarantines worker artifact rows in the saved summary; the dashboard also hides unverified rows in older failed reports from counts, filtering, comparison, and downloads. Harmless hardlink probes cover summaries, engine reports, manifests, and artifacts; other filesystem races and reparse types remain unproven.

## Managed static initialization

The CIL interpreter supports tested `ldsfld` and `stsfld` operations, simple unassigned static-field defaults, and one-time `.cctor` execution. Explicit static constructors run before first modeled static method or instance construction; `beforefieldinit` initializers run when a static field is accessed. Direct field references to a named, explicitly supplied managed DLL match its public field name and CIL signature. Static values remain scoped to that loaded module; instance values remain on a guest object belonging to it. Generic and thread-local fields, field address operations, broader reference kinds, and exact CLR initialization timing remain unsupported or incomplete.

## Managed embedded resources

Tested `Assembly.GetExecutingAssembly`, `GetManifestResourceNames`, and `GetManifestResourceStream(string)` use bytes from the guest assembly or an explicitly supplied managed DLL. Embedded resource offsets and sizes must stay within the PE's declared CLR resource section; each opened resource is capped at 32 MiB and distinct opened resources at 64 MiB per run. Opening a resource records its bytes as an analysis artifact and returns a read-only guest stream; `CopyTo` can move them into guest memory or files. External linked resources, localized satellite assemblies, `.resources` object decoding, other overloads, and exact runtime stream type behavior remain incomplete.

## Virtual allocation release

`VirtualFreeEx` checks the target handle, VM operation right, allocation base, owner, and `MEM_RELEASE` parameters before marking an emulated allocation released. `VirtualFree` applies the same base and release checks to the current process. Release attempts are recorded in `virtual_process_events`; later bridge-mediated reads, writes, protection changes, and remote-thread starts against tracked released ranges fail. Successful releases snapshot up to 4 MiB of nonempty owned guest allocation bytes before destruction, with explicit omissions for unreadable or over-budget pages; changing an owned allocation to executable protection also snapshots it. Freed maps are excluded from final live-memory artifacts. The engine may retain their backing bytes, so reuse can still diverge from Windows. `MEM_DECOMMIT`, placeholders, and other allocation provenance remain unsupported.

The harmless `virtual_free_ex_x86.exe` and `virtual_free_ex_x64.exe` fixtures test a nonzero-size rejection, a successful release, and a repeated-release rejection. Run each through the packaged CLI into `output/virtual-free-package/x86` and `output/virtual-free-package/x64`, then run `.venv\Scripts\python.exe tools\verify_virtual_free_fixtures.py output\virtual-free-package` to check the guest exit path, API results, released-map state, artifact hashes, and broker closure.

## Known-owner CPU memory guard

Guest CPU read, write, and instruction hooks stop tested direct access to pages owned by a different modeled guest process, and direct reads of tracked released pages. A denied write is restored before the engine snapshots memory or schedules another guest run; single stores and `rep stosb` leave the child page unchanged in x86/x64 fixtures. If rollback fails, queued guest runs and child execution are halted. `virtual_cpu_memory_denied` and `virtual_cpu_memory_restored` events explain the result. The underlying emulator still has one memory arena, and ownership metadata is incomplete for some mappings. These hooks and rollback do not establish Windows-grade private address spaces or protection against every possible instruction sequence.

The modeled `kernel32`/`ntdll` `RtlMoveMemory`, `RtlCopyMemory`, and `RtlZeroMemory` calls, plus `msvcrt` `memcpy`, `memmove`, `memset`, and `memcmp`, also check known owner and released ranges before their Python handlers access guest bytes. Invalid or oversized transfers stop the guest and record `virtual_memory_api_denied`. Harmless x86/x64 EXEs attempt `RtlMoveMemory` from a child allocation into a parent buffer; the API call is denied after a legitimate `WriteProcessMemory` succeeds. This guard covers the listed handlers, not every API that can inspect guest pointers.

The `kernel32` `lstrlen`, `lstrcmp`, `lstrcmpi`, `lstrcpy`, `lstrcpyn`, and `lstrcat` ANSI/Unicode handlers scan guest strings through bounded, owner-checked reads and check any destination range before their Python handlers run. The `child_api_string_*` fixtures test a denied child-page `lstrcpyA` copy; `local_api_string_*` fixtures check a permitted same-process copy. Other string APIs and other handler families still need the same review.

A dispatch guard also checks guest-memory reads and writes made by installed Python API handlers through Speakeasy's memory methods. Known child-owned or released ranges stop the guest before the handler can consume them; `virtual_handler_memory_denied` records the API, access, address, size, and reason. The modeled `ReadProcessMemory` and `WriteProcessMemory` handlers grant a narrowly scoped exception for a target range only after handle-rights and ownership validation. `child_api_env_*` fixtures exercise a previously unguarded `GetEnvironmentVariableA` child-pointer read; `local_api_env_*` fixtures confirm a permitted local environment read. This guard does not create private address spaces, cover every possible engine-internal path, or prove arbitrary-sample safety.

For maps created inside imported API handlers, the dispatch layer assigns an unspecified private map to the current guest process. It preserves an explicit owner and maps marked shared. This covers untagged handler allocations in the installed engine; actual parent/child probes for those handlers and direct engine-map operations remain open.

Imported handlers are also stopped before they request a nonpositive or over-32 MiB map, or an untagged map at the reserved `0x1000` page.
